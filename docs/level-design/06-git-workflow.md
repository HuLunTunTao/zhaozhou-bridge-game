# 06 -- Git 工作流

> 本章介绍如何使用 Git 来管理关卡场景和资源文件，避免多人协作时的冲突，保持版本历史清晰可追溯。

---

## 6.1 为什么要用 Git

Git 是版本控制工具，帮助你：

- **记录每次改动**：随时回退到之前的版本
- **多人协作**：多个设计师可以同时编辑不同关卡
- **冲突检测**：当两个人修改了同一个文件时，Git 会提醒你
- **代码审查**：提交前可以查看自己改了什么，避免意外提交

---

## 6.2 Godot 项目中的文件格式

理解文件格式对 Git 协作很重要：

| 文件类型 | 扩展名 | 格式 | 说明 |
|----------|--------|------|------|
| 场景文件 | `.tscn` | 文本 | 可以 diff、可以 merge（但不建议手动 merge） |
| 资源文件 | `.tres` | 文本 | 可以 diff、可以 merge |
| GDScript | `.gd` | 文本 | 标准文本文件，和代码一样处理 |
| 图片 | `.png` / `.jpg` | 二进制 | 不可 diff，冲突时只能选择一方 |
| 导入缓存 | `.godot/` 目录 | 二进制 | **已被 .gitignore 排除**，不会提交 |

> 💡 提示: `.tscn` 和 `.tres` 虽然是文本格式，但它们的内容是 Godot 的序列化格式，包含很多 `[node]`、`[sub_resource]` 等标记。用文本编辑器可以打开查看，但通常不需要手动编辑。

---

## 6.3 .gitignore 说明

项目根目录下的 `.gitignore` 文件已配置好，排除了以下内容：

| 排除项 | 原因 |
|--------|------|
| `.godot/` | Godot 编辑器的缓存和导入数据，每台机器自动生成 |
| `/android/`、`/build/`、`*.apk` 等 | 构建产物 |
| `.DS_Store`、`Thumbs.db` | 操作系统生成的隐藏文件 |
| `.vscode/`、`.idea/` | IDE 配置文件 |

你不需要修改 `.gitignore`，除非项目中新增了需要排除的文件类型。

## 6.4 日常工作流

### 开始工作前：拉取最新代码

**每次打开项目开始工作前**，先拉取远程仓库的最新代码：

```bash
git pull
```

这一步能确保你基于最新版本进行修改，减少后续冲突的可能性。

> ⚠️ 注意: 如果 `git pull` 提示有冲突（conflict），先解决冲突再继续编辑。不要在有未解决冲突的状态下打开 Godot 编辑器。

### 工作中：频繁保存，定期查看变更

1. 在 Godot 编辑器中正常编辑关卡
2. 经常按 `Ctrl+S` 保存
3. 工作到一定阶段后，在终端中查看当前改动：

```bash
git status          # 查看哪些文件被修改了
git diff            # 查看具体改了什么内容
```

### 完成工作后：提交变更

编辑完成后，将改动提交到 Git：

```bash
git add scenes/levels/level1-5/       # 添加你修改的关卡文件夹
git commit -m "关卡1-5: 完成地图绘制和单位放置"
git push                              # 推送到远程仓库
```

## 6.5 提交粒度与规范

### 原则：一个关卡一次提交

**不要把多个关卡的改动混在一起提交。** 每次提交应该只涉及一个关卡（或一个逻辑单元）的改动。

好的做法：

```bash
# 提交 1：关卡 1-5 的地图
git add scenes/levels/level1-5/
git commit -m "关卡1-5: 完成地图绘制"

# 提交 2：关卡 1-6 的地图
git add scenes/levels/level1-6/
git commit -m "关卡1-6: 完成地图绘制"
```

不好的做法：

```bash
# 把两个关卡的改动混在一起
git add scenes/levels/level1-5/ scenes/levels/level1-6/
git commit -m "完成了一些关卡"  # 不清楚改了什么
```

### 提交信息格式

推荐使用以下格式：

```
<范围>: <做了什么>
```

| 范围示例 | 说明 |
|----------|------|
| `关卡1-5` | 某个具体关卡 |
| `data/units` | 单位数据 |
| `data/skills` | 技能数据 |
| `docs` | 文档 |

具体示例：

```
关卡1-5: 完成地图绘制和单位放置
关卡1-5: 调整敌方泥鬼属性为精英版
data/units: 新增精英坍岸泥鬼数据文件
关卡1-3: 修复工匠队伍配置中的节点路径错误
```

### 什么时候提交

- 完成了一个可运行的阶段性成果（如地图画完、单位配好、能跑起来了）
- 完成了一项独立的修改（如调整了某个敌人的数值）
- **下班之前**：把当天的工作提交并推送，避免数据丢失

> ⚠️ 注意: 提交前务必用 `git diff` 检查改动，确认没有意外修改到共享资源文件（如 `data/units/` 下的 `.tres`）。参见 [05-资源唯一化](05-resource-uniqueness.md)。

## 6.6 分支策略

### 推荐：每个关卡使用独立分支

当多人同时开发不同关卡时，建议每个关卡使用自己的 feature branch：

```bash
# 创建并切换到新分支
git checkout -b level/1-5

# 在此分支上进行关卡开发 ...
# 开发完成后推送到远程
git push -u origin level/1-5

# 开发完成后，创建 Pull Request 合并到 main 分支
```

分支命名建议：

| 类型 | 命名格式 | 示例 |
|------|----------|------|
| 关卡开发 | `level/<关卡编号>` | `level/1-5` |
| 数值调整 | `balance/<描述>` | `balance/enemy-hp-rebalance` |
| 文档更新 | `docs/<描述>` | `docs/update-skill-reference` |

### 合并到主分支

关卡开发完成后，通过 Pull Request (PR) 合并到 `main` 分支：

1. 在 GitHub 上创建 PR
2. 请其他人审查（主要检查：共享资源是否被意外修改、关卡是否能正常运行）
3. 审查通过后合并

> 💡 提示: 如果团队规模小（2-3人），也可以直接在 `main` 分支上工作。关键是**每次开始工作前先 pull，提交粒度保持清晰**。

## 6.7 场景文件冲突处理

当两个人同时修改了同一个 `.tscn` 或 `.tres` 文件时，Git 会报告冲突。

### 处理原则

**对于 `.tscn` 场景文件：不要尝试手动 merge。**

`.tscn` 文件中的节点 ID、SubResource ID 等是 Godot 自动生成的，手动编辑极易出错。正确做法：

1. 与对方沟通，确定**以哪一方的版本为准**
2. 选择保留一方的版本：

```bash
# 保留自己的版本
git checkout --ours scenes/levels/level1-5/level1-5.tscn

# 保留对方的版本
git checkout --theirs scenes/levels/level1-5/level1-5.tscn
```

3. 标记冲突已解决并提交：

```bash
git add scenes/levels/level1-5/level1-5.tscn
git commit -m "关卡1-5: 解决场景文件冲突，保留了xxx的版本"
```

4. 被放弃的那一方需要在新版本基础上重新应用自己的改动

### 对于 `.tres` 数据文件

`.tres` 文件结构相对简单（基本是 key = value 格式），**小范围冲突可以手动 merge**：

```ini
# 冲突区域示例
<<<<<<< HEAD
max_hp = 130
=======
max_hp = 150
>>>>>>> other-branch
```

根据实际需要保留正确的值，删除 `<<<<<<`、`======`、`>>>>>>` 标记即可。

### 对于 `.gd` 脚本文件

GDScript 是普通文本文件，可以像正常代码一样手动 merge。

### 如何避免冲突

最有效的方式是**避免多人同时编辑同一个文件**：

- 不同设计师负责不同关卡，各自的文件互不重叠
- 共享资源文件（`data/units/*.tres`、`data/skills/*.tres`）的修改由一个人统一管理，或者通过 Make Unique 创建独立副本（参见 [05-资源唯一化](05-resource-uniqueness.md)）
- 改动前先沟通："我要改 game_state.gd 加一个关卡入口，你先别改这个文件"

## 6.8 常用 Git 命令速查

| 命令 | 作用 |
|------|------|
| `git status` | 查看当前有哪些文件被修改、新增或删除 |
| `git diff` | 查看文件的具体改动内容 |
| `git diff <文件路径>` | 查看指定文件的改动 |
| `git add <文件或文件夹>` | 将改动添加到暂存区（准备提交） |
| `git commit -m "提交信息"` | 提交暂存区的改动 |
| `git push` | 将本地提交推送到远程仓库 |
| `git pull` | 从远程仓库拉取最新代码 |
| `git log --oneline -10` | 查看最近 10 次提交记录 |
| `git checkout -- <文件>` | 放弃某个文件的未提交改动，恢复到最后一次提交的状态 |
| `git stash` | 临时保存当前改动（切换分支前使用） |
| `git stash pop` | 恢复之前临时保存的改动 |

---

## 6.9 Git 工作流检查清单

每次工作结束前，确认以下事项：

- [ ] `git status` 没有意外修改的文件（特别注意 `data/` 目录下的共享资源）
- [ ] `git diff` 中的改动都是预期的
- [ ] 提交信息清晰，说明了改了哪个关卡、做了什么
- [ ] 每个提交只涉及一个关卡或一个逻辑单元
- [ ] 已经 `git push` 到远程仓库
